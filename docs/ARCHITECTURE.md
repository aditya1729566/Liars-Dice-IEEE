# Architecture

The C++20 engine receives JSON commands and returns JSON results. It alone rolls dice, checks quantity-only raises, resolves challenges, awards points, and manages `BIDDING`, `ROUND_OVER`, and `MATCH_OVER`. A Python standard-library HTTP adapter stores private state in SQLite and passes validated commands to the engine. Invalid attempts are logged separately and leave state unchanged. Browser views hide the AI hand until reveal; matches resume by opaque ID. The Next.js client renders the authoritative view with DOM/CSS 2D dice and asks the API to start the next round. Evaluation tooling invokes the same compiled agents with deterministic seeds and records their decisions, reveals, and policy hits.

The engine saves a private record before each AI decision: its hand, the public bid, the chosen action, the exact five-unseen-dice binomial prior for that bid or action, and the sampled policy's action weight when one was used. This record is omitted from ordinary game views. The HTTP adapter serves it through `GET /api/matches/{id}/research` only after the match is complete. `server/replay.py` then joins the authoritative event log, completed-round hands, and recorded AI decisions into ordered slides. It inserts a challenge slide before each reveal because the event log represents the challenge as a reveal event. Human-move interpretations use only the AI's own hand and public bid; both hands and actual counts are displayed separately as post-match ground truth. The browser keeps a session-local list of completed opaque IDs for the Research journal; it does not enumerate other visitors' matches.
